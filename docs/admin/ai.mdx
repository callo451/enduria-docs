# AI settings

Control which assistance your team can use and review proposed changes before they run.

> **Availability:** The revised classification controls, action-state labels and shared module access rules described here are awaiting application rollout. Until rollout is confirmed, your screen may show older labels. The central agent workspace and broader module automation are planned separately.

## Before you start

Open **Settings → Artificial Intelligence**. Viewing configuration requires `ai.config.view`; saving requires `ai.config.edit`. The settings navigation is available to administrators. Staff use of Copilot also requires `ai.copilot.use`, an allowed role, and the relevant permissions for the records or actions requested.

Your operator must configure an AI provider for this deployment. The **Models** tab shows the configured provider and model tiers. Tenant settings choose tiers; they do not supply provider credentials.

## Enable ticket suggestions

1. Configure active priorities for the work-item types your team uses and active, unrestricted service-catalogue categories. Automatic suggestions currently omit categories restricted to selected customers or staff.
2. Open the **Features** tab and enable **Enable Smart Classification**.
3. Enable **Suggest Classification on New Tickets**.
4. Select **Save Configuration**.
5. Open a newly created ticket. If classification succeeds and the ticket remains unchanged while it is generated, its workspace shows **AI suggestion awaiting review**.
6. Review the category, priority and confidence. Use the ordinary ticket fields to apply appropriate changes.

Suggestions do not change the ticket's type, category, priority, queue, assignee or status automatically. Confidence is a guide for review, not permission to execute a change. If the ticket changes during generation, a stale suggestion is discarded.

**Enable Auto-Resolution** is unavailable. Matching knowledge or offering an answer does not confirm that an issue is resolved. **Auto-Generate on Ticket Resolve** is also unavailable; use the supported manual article-drafting workflow instead.

## Review proposed actions

Read [Using AI assistance](../product/ai-assistance.mdx) for the review steps. A proposal must use current configured vocabulary and your current permissions. AI approval does not replace a separate required ticket approval: if that review is required, create the request through its ordinary workflow.

Ticket investigation requires the appropriate ticket-view permission. Creating a general ticket requires `tickets.create`; creating an incident requires `tickets.createIncident`. Knowledge retrieval requires `kb.view` and the article's category access. These permissions do not grant access to other modules. Portal assistance uses the current requester's ticket scope and customer-visible published knowledge, including client audiences.

## Control module access

Staff assistance uses the relevant module permissions in addition to AI access. Staff accounts bound to a client must use their supported portal assistance; the staff AI surfaces do not provide tenant-wide access for those accounts.

| Information requested | Required scope |
| --- | --- |
| Asset register and reported device facts | `assets.view` for unbound staff |
| Directory profiles | `users.view`; profiles exclude credentials and permission overrides |
| Projects | `projects.view.all`, managed projects through `projects.view.own`, or member projects through `projects.view.assigned` |
| Project financial facts | Accessible project plus `projects.budget.view` |
| Service catalogue | `catalog.view`, active items and the customer's current audience where applicable |
| Ticket analytics | `tickets.view.all` or `tickets.view.own`; totals retain the account's ticket scope |

AI Search can return bounded charts and tables. A truncated group list does not mean the remaining records are absent. SLA reports keep response and resolution outcomes separate; missing clocks remain unknown. Asset analyses count active register records by default. An asset's configured status and operational state are separate facts.

Communication drafts prepare text for review. They do not send emails or notifications. Classification and queue guidance apply no changes. Catalogue guidance opens the selected service's normal request form; it does not submit a service request or bypass required fields and approvals.

These staff capabilities do not expand the existing MCP endpoint. Its dedicated keys still support the documented ticket operations. [Agent access](agent-access.mdx) prepares separately reviewed module/action policies and is awaiting rollout; new external connections and broader automation remain planned.

## Review an external agent's ticket proposal

> **Availability:** The revised MCP review, cancellation and stale outcomes are awaiting application rollout. Existing saved proposals retain their original approval and rejection flow.

An external MCP client can prepare a general support ticket and return a review link. Its dedicated key cannot approve or create the ticket. Review requires an active staff account with no client binding and both `tickets.create` and `tickets.view.all`. It does not require Copilot to be enabled.

1. Open the returned Enduria review link and sign in with your staff account.
2. On **Review ticket proposal**, check the title, description, priority and category. You will become the ticket requester and be recorded as its creator and approver.
3. Select **Approve and create ticket**, **Reject**, or, for a new proposal, **Cancel proposal**.
4. Read the recorded status. An **executed** result includes a link to the created ticket. Rejection and cancellation create no ticket.

New proposals expire after at most 30 minutes, or sooner if the proposing key expires. Current staff permissions, key authority, API enablement and configured ticket choices are checked again at approval. If relevant configuration changed, the proposal becomes **stale** and no ticket is created. Request a fresh proposal and review its updated fields. A required ordinary ticket approval must still use the normal ticket workflow.

If a decision response is lost, retry the same decision or select **Reload proposal** to inspect its recorded outcome before asking the client for another proposal. The client must reuse its request key for retries of the same fields. Different fields require a new request key and review. If the proposing key was revoked, approval is refused; an authorised reviewer can still inspect and reject or cancel the saved intent.

Read-only MCP keys can search bounded organisation-wide ticket summaries; they cannot prepare proposals. The existing MCP tools do not provide asset actions, assignment, remote remediation or OAuth connection setup. An operator must enable and configure the endpoint before an external client can connect.

## Limits and retained evidence

Use **Security** to configure request limits and log retention. Mandatory action decisions and scheduled delivery claims are kept separately from ordinary expiring telemetry so retrying an old operation cannot repeat its effect. This release does not provide automatic content purging for those retained decisions.

## Common problems

| Problem | Next step |
| --- | --- |
| Configuration cannot load | Select **Retry**. Ask an administrator to check your configuration permissions if it persists. |
| No classification suggestion appears | Check feature settings, active categories and applicable priorities, provider availability, and request limits. A changed ticket may require a new manual investigation. |
| Proposal is unavailable or expired | Start a new proposal with current information. Do not reuse a decision from another account. |
| A separate ticket approval is required | Use ordinary ticket creation and its configured review. |
| The assistant fails to respond | Retry the response or contact your operator. Check the action's current status before asking for another change. |
