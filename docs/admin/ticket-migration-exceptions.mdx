---
title: Review ticket handover exceptions
description: Review handover responses, retain actual reversal facts, approve future recovery instructions and independently verify performed evidence.
---

> **Awaiting application rollout.** Handover exception recording and response
> review and performed-fact recording are awaiting application rollout. Linked
> recovery controls also await application rollout. Documentation publication does not
> establish availability in your Enduria deployment.

> **Awaiting application delivery and rollout.** Independent performed verification
> and the explicit no-executor choice described below are not yet delivered.
> Confirm their availability in your deployment before using those steps.

Use **Settings → Service Management → Ticket migration → Review handover
exceptions** when an issue is discovered after an independently confirmed ticket
handover. Keep the original handover, the observed issue and each response decision
as separate evidence. A response can acknowledge the issue for separate handling
or propose an explicitly manual routing reversal.

Approval changes no source routing, mailbox configuration, ticket, assignment or
SLA clock. It records no performed reversal. Use the separate performed-facts step
to retain what actually happened. Linked recovery approval records separately
reviewed future instructions. Independent performed verification records a separate
decision against original facts and current evidence; it never repeats an action.
Source shutdown
and application rollout remain separate responsibilities. Imported backlog keeps
**no SLA clocks**.

## Required access

Recording, reading, reviewing and recovering these commands require current
active unbound staff with `settings.manage`, `tickets.manage`, `tickets.view.all`
and `tickets.edit.all`. Portal customers and client-bound staff cannot administer
this workflow. A response reviewer must differ from that response's proposer.
For linked recovery, the reviewer must differ from both the original response
proposer and the recovery proposer. The recovery proposer must still hold current
migration administration access when the new proposal is approved.
For performed verification, the reviewer must differ from the verification-case
proposer, performed recorder and every actual staff executor. The case proposer
must still have current migration administration access at successful confirmation.
The original issue proposer alone can cancel the exception before any response
decision. Naming an external operator grants no Enduria access.

Any currently authorised administrator can propose a response revision. If the
original author leaves or loses access, another administrator can continue the
response process, with fresh independent review.

## Record the observed issue

1. Open an independently [confirmed performed handover](./ticket-migration-handover)
   and choose **Record or review a handover exception**. Alternatively, open
   **Review handover exceptions**, choose the **Registered source**, use
   **Load source handovers**, select the retained handover and choose
   **Check handover confirmation**.
2. Expand **Record a handover exception**. Under **Record the observed issue**,
   choose the **Issue classification** and give the **Actual detection time
   (UTC)**, **Observed issue** and **Operational impact**. Classification describes
   the migration issue; it does not change your ticket statuses or priorities.
3. If relevant, expand **Optional related existing tickets**, search a ticket
   number or title, and select up to 20 existing records. References create no
   incident and change no existing ticket work.
4. Give the **Record action reason** and choose **Record exception**.
5. After the command is confirmed, choose **Inspect current exception**. The
   record pins the original source, client, final manifest and independent
   handover confirmation. Inspect its issue, impact and intervening-work coverage.

The detection time must describe a performed observation, not a future event.
Use **Load handover exceptions** to find earlier issues for the same handover.
**Open a retained exception by reference** is available when you already have
its UUID.

## Choose and compare the response

1. Inspect the current exception and expand **Prepare a response revision**.
2. Under **Response choice**, select either **Record the issue for separate
   handling** or **Propose a manual routing reversal**. Give the
   **Response explanation**.
3. For a manual reversal proposal, complete the operator attestations, original
   path instructions, current mailbox dispositions and changed-work dispositions
   described below. Leave uncertainty explicit until it has been resolved.
4. Give the **Response action reason** and choose **Compare response evidence**.
   Read the coverage and every blocker. An incomplete proposal can be retained
   for review, but cannot approve a manual reversal.
5. Choose **Record response revision**. Another authorised administrator must
   inspect that exact revision before deciding.

A log-only response can retain an issue when interval coverage is unknown. Its
acknowledgement certifies no routing, reconciliation or history continuity.

### Account for manual reversal scope

Keep every original path named and preserve its included or excluded scope.
Original exclusions stay excluded; expanding routing requires separate
operational authorisation. For each path, give the manual action or retained
exclusion, intended destination, responsible operator, verification method and
recovery instructions. Included paths also need an ordered intended execution
window in UTC.

Account for every currently registered local mailbox and every observed changed
identity. State whether each belongs to this migration, sits outside this reversal
scope with a reason, or remains unresolved. A changed-work disposition also needs
the retained work location, manual reconciliation owner and instructions. These
locations and responsibilities are operator attestations. They do not copy,
replay, delete, merge or compensate work.

Changed-work forms and retained review are paged. Inspect all pages, including
work outside the selected backlog. The same identity in different observation
domains counts separately. A deleted record can remain in the observation
inventory without its historical content being available. Current client or
channel alone cannot establish the record's earlier scope after a move.

### Understand interval coverage

New handover confirmations retain a forward observation baseline. Earlier
confirmations without that baseline remain readable but have **legacy unknown**
coverage; no historical interval is manufactured. A fresh performed-handover
proposal and independent confirmation can establish a new forward interval,
while the earlier unknown interval remains explicitly unresolved.

Manual reversal approval requires complete current coverage and dispositions for
all observed changes. More than 200 changed identities, an oversized inventory,
missing evidence or unresolved entries make coverage incomplete. Use a separately
scoped operational process when the supported bounds cannot cover the work.

Observation counts cannot prove uninterrupted history. A restore or other history
discontinuity requires separate reconciliation of the missing interval. Record
the uncertainty and establish a new forward baseline; an acknowledgement cannot
certify the missing period. External routing inventories and continuity remain
operator attestations, even when the Enduria comparison is complete.

## Review independently

1. A different authorised administrator opens the retained exception and inspects
   **Review response independently**. New issue and response preparation tools
   collapse so the review stays in focus.
2. Inspect the exact revision, response explanation, current coverage, original
   path instructions, mailbox dispositions and every changed-work page. Current
   comparison and retained approval are separate facts.
3. Give the **Independent review reason**, then choose **Approve response** or
   **Reject response**. Approval is unavailable when current evidence or authority
   has changed, the revision was replaced, or required coverage is incomplete.
4. Use **Retain current response comparison** to keep a later point-in-time
   comparison. Use **Load response revisions** and **Load retained comparisons**
   to inspect earlier evidence.

At most one active approved manual reversal response can cover the whole handover.
Log-only responses can coexist. New ticket work or mailbox changes can make
current readiness unavailable without rewriting the original approval.

## Replace or cancel a proposal

A newer pending response revision closes the earlier review token. The older
revision stays visible and cannot later be approved.

Replacing an approved response requires two separate decisions. Record the
replacement revision first; the existing approval remains current. An authorised
reviewer different from both response proposers inspects the replacement and uses
**Supersede unexecuted approval** to retire the earlier approval. The replacement
then needs a fresh independent **Approve response** decision. Supersession does
not authorise the replacement or reverse any performed action.

The original issue proposer can use **Cancel undecided exception** before any
response decision. Cancellation retains the issue and its revisions. An approved,
rejected or cancelled record is never edited or erased.

## Recover an unconfirmed result

1. Keep the displayed original command UUID and use the original account.
2. After access is restored, open **Recover an exception command** and choose
   **Look up exception command** for that UUID.
3. If the exact original request remains available, **Retry exact exception
   command** safely repeats that request. Do not create a replacement UUID while
   the original result remains unconfirmed.
4. Once the matching receipt is confirmed, inspect the current exception before
   another action.

Editing and new writes stay paused while the result is unconfirmed. Losing
authority clears sensitive screen data; it does not grant receipt access. Restore
current migration administration authority before recovering with the original
account.

Before performed evidence is retained, a changed comparison requires inspecting
the current evidence and recording a new response revision before approval. If
another manual reversal response is already approved, reconcile that retained plan
before proposing competing routing. After performed evidence is retained, ordinary
revision and supersession are unavailable; use your separate manual operational
process or the separately reviewed linked recovery workflow below. New instructions
never overwrite the earlier actual facts.

## Retain performed manual reversal facts

Retain what already happened against a historically approved manual response.
This step does not execute routing or independently verify a result. It permits
partial, failed and unknown facts, including after the original actors leave,
configuration changes or the approval is superseded.

1. Inspect the appropriate retained response revision. Choose **Inspect performed
   reversal evidence** beneath its historical approval.
2. In **Retain performed manual reversal facts**, enter the actual episode summary
   and authorisation circumstances. Describe known continuity or its uncertainty.
   Give an external report reference and SHA-256 when available, or explain their
   absence. Enduria does not fetch the reference.
3. Expand each original path, including excluded paths. Record its actual outcome,
   action and destination where known. Give actual start/end times in UTC, or leave
   them unavailable with a reason. Do not substitute an intended execution window.
4. Identify the actual executor. Search **Known tenant staff identity** for an
   existing staff person; inactive identities can be retained. Alternatively choose
   **External or unresolved identity**, retaining any known name/reference and why
   an enforceable identity is unavailable. Naming someone grants no access.
   For an excluded path that was not performed, choose **No executor — excluded
   path was not performed** and give the reason. This choice requires unavailable
   actual action, destination and start/end times. Do not use it for an included or
   executed path, and do not invent an executor for an action that never occurred.
5. State whether the action matched the plan, describe the comparison/deviations,
   and retain the work's location and manual reconciliation responsibility/instructions.
6. Give the **Performed record reason**. Choose **Compare performed evidence** and
   inspect the fresh observation and uncertainties. Choose **Record performed facts**.
7. After the command is confirmed, inspect the response and performed episode again.
   Recover an unreadable result using the original command UUID and account as
   described above. Do not issue a new command to repeat a manual action.

Only one immutable episode can be recorded for a response. Recording closes further
execution under that approval and ordinary supersession; the original approval and
reserved handover plan remain. Late facts against a superseded approval do not
reactivate it or take another plan's reserved slot. The retained observation is a
point-in-time comparison, not proof that external routing succeeded.

The original observation remains **unverified when retained**, even if a separate
independent confirmation is recorded later. Partial, failed, not-performed or
unknown results on an included path need explicit future handling. Retaining
uncertain facts is not permission to repeat routing or
compensate tickets, and does not establish source shutdown or application rollout.

## Propose linked future recovery

Use linked recovery when the retained performed episode belongs to the current
reserved manual response. Late facts for an already superseded response cannot
take another plan's reservation. Keep the earlier episode visible while reviewing
future instructions.

1. Inspect the original approved response and choose **Inspect performed reversal
   evidence**. Read its retained actual outcomes and uncertainty first.
2. Choose **Inspect linked recovery**. Enduria checks the original episode and
   current reserved response. If that response no longer owns the reservation,
   inspect the current exception and plan before taking further action.
3. Expand **Prepare linked recovery proposal** and choose **Prepare current recovery
   draft**. This reads the current inventory and starts a draft; it performs no
   manual action. **Refresh current inventory and reset draft** deliberately replaces
   the current draft with a fresh empty form.
4. Give the **Future recovery explanation** and **Handling earlier uncertainties**.
   Under **Handling retained actual outcomes**, account for every original path,
   including excluded paths. Choose **Retain completed work**, **Continue remaining
   work**, **Use a separate manual process** or **Unresolved**. Give an explanation,
   retained actual work location, reconciliation owner and instructions for each.
5. Complete the **Future manual response** using the original path scope, intended
   action/window, operator attestations, current mailbox dispositions and every
   changed-work page. Earlier actual times or outcomes remain unchanged. Do not
   repeat an uncertain action merely because a new proposal exists.
6. Give the **Recovery proposal reason**, then choose **Compare recovery proposal**.
   Inspect the original handover interval, current coverage and all blockers.
   An unresolved proposal can be retained when its required explanations are
   complete; it cannot be approved.
7. Choose **Record recovery proposal**. After command confirmation, inspect the
   original performed episode and **Inspect linked recovery** again. The latest
   proposal appears under **Review linked recovery independently**.

Recording creates no replacement response and releases no reserved plan. A newer
recovery proposal makes earlier undecided reviews obsolete while retaining their
evidence. Use **Retained recovery proposals → Load recovery proposals** to inspect
earlier revisions.

## Review linked recovery independently

1. Another currently authorised administrator opens the original exception,
   inspects its approved response and performed episode, and chooses
   **Inspect linked recovery**.
2. Read **Review linked recovery independently**: the exact proposal, earlier
   uncertainty handling, retained actual-outcome handling and proposed future
   response. Inspect every mailbox and changed-work page, including work outside
   the selected backlog.
3. Give the **Independent recovery review reason**. Choose **Approve linked recovery**
   or **Reject linked recovery**. Approval is unavailable if the reviewer matches
   either proposer, the current recovery proposer loses access, the comparison
   changes, required coverage is incomplete or handling remains unresolved.
4. After approval is confirmed, choose **Inspect current exception**. The exact
   replacement response and its independent approval become current together.
   The original response, performed episode and uncertainties remain retained.

Approval transfers the handover's single reserved manual plan to the exact
replacement. It approves only future manual instructions, performs no routing and
certifies no earlier result. A pending ordinary response revision is retained but
becomes obsolete when the governed replacement advances beyond it.

Rejection creates no replacement and leaves the original reservation intact.
Prepare a new proposal if different future instructions are needed. Historical
authors leaving does not prevent a different currently authorised proposer and
independent reviewer from continuing this process.

If work or configuration changes during review, inspect the current evidence
and prepare a fresh proposal. If the result is unreadable, recover the original
command UUID with the original account before issuing another command. The
receipt identifies the original episode, recovery proposal/decision and exact
replacement reference; it is not evidence that any manual action succeeded.

A later performed episode against the approved replacement needs its own retained
facts and separately reviewed recovery, if required. Earlier episodes are never
reopened, rewritten or automatically compensated. Independent verification,
source-system operations and application rollout remain separate.

## Prepare verification evidence

Use verification to review one exact retained episode of an independently approved
manual response. Read the original instructions, actual facts and uncertainties
first. A current response must own the reserved scope before a new case can be
prepared; old evidence cannot take a later response's reservation.

1. Inspect the retained approved response and choose **Inspect performed reversal
   evidence**. Beneath the original episode, choose **Inspect independent verification**.
2. Read the separate confirmation and current-readiness summary. Expand **Prepare
   verification evidence** and choose **Prepare current verification draft**.
   **Refresh verification inventory and reset draft** replaces the draft with a
   fresh empty form; it changes no routing or work.
3. Give the **Verification explanation**. Under **Original path evidence**, expand
   each original path and explain its **Verification evidence for this original
   path**. Original path names, included/excluded scope and execution facts stay fixed.
4. Under **Mailbox effects**, review every page and give explicit effect evidence
   for every original/current mailbox identity. Choose **Configuration unchanged**,
   **Observed approved change**, **Outside this migration scope** or **Unresolved
   effect**. An observed approved change needs the **Exact approved mailbox path**.
   Enduria offers only original included paths bound to that exact account.
5. Under **Intervening work**, review every changed identity from the original
   handover interval. Choose its **Changed work scope** and give scope/disposition
   evidence, retained location, reconciliation owner and instructions. Deleted or
   unavailable content stays unavailable; today's client or channel does not prove
   an earlier source scope.
6. Give the **Verification record reason** and choose **Compare verification
   evidence**. Read the coverage and all blockers. Choose **Record verification case**.
   Incomplete evidence can be retained for review, but cannot be confirmed.
7. After command confirmation, inspect the current exception and original episode
   again, then choose **Inspect independent verification**. The latest case appears
   under **Review performed verification independently**.

Configuration fingerprints describe observed state. They do not authorise a change
or replace the approved action/destination and actual execution evidence. An
included web path cannot establish an approved mailbox effect; an included mailbox
cannot be reclassified outside the migration to avoid review. Unresolved effects,
missing identities or incomplete interval coverage block successful confirmation.

Verification cannot fill in unknown original times, executor identities, outcomes,
continuity or report references. A later performed recovery needs its own retained
episode and independent verification; it does not make an earlier unknown episode
successful. Excluded paths that were not performed remain exclusions.

## Review performed verification independently

1. Another currently authorised, independent administrator opens the original
   exception and performed episode, then chooses **Inspect independent verification**.
2. Read **Review performed verification independently**: the exact case revision,
   explanation, original-path evidence, current comparison and blockers. Expand
   **Inspect current comparison pages** and inspect the paths, mailboxes and work
   pages. Mailbox comparisons include approved/current fingerprints and the exact
   retained path binding; work comparisons retain each disposition and responsibility.
3. Give the **Independent verification review reason**. Choose **Confirm performed
   verification** or **Reject verification case**. Confirmation is unavailable for
   a non-independent account, superseded case, changed evidence, lost proposer
   access, unresolved original facts or incomplete required coverage.
4. After command confirmation, inspect the episode and independent verification
   again. Successful confirmation is retained separately from the original
   performed observation. Only one successful confirmation can stand for an episode.

Rejection preserves the original facts and reservation. A fresh case can be prepared
if the immutable original facts support it. A newer case makes an earlier undecided
review obsolete while retaining its evidence. Use **Retained verification cases →
Load verification cases** to inspect earlier revisions.

## Understand confirmation and current readiness

**Independent confirmation retained** means an independent decision was recorded
against that episode and comparison at the time. **Current evidence still matches
that confirmation** is a separate, fresh observation. Later ticket/mail/configuration
changes, including a change that was reverted, can make current readiness unavailable
without rewriting the earlier confirmation. Historical actors leaving alone does
not erase retained facts or confirmation; current readers still need administrator
access.

Further execution under the performed response remains closed after confirmation.
Verification releases no reservation and changes no routing, ticket, assignment,
SLA clock or source shutdown. Use separately reviewed linked recovery for new
future instructions when needed.

If a write result is unreadable, preserve the original command UUID and recover it
with the original account using **Recover an exception command**. New writes stay
paused until that result is confirmed. After access loss, protected forms are
cleared; restore current access and look up the original UUID before continuing.
The receipt binds the original episode, case/decision and evidence fingerprints;
it does not establish application rollout or completion of source-system operations.
