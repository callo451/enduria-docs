> **Awaiting application rollout.** The ticket migration workspace and review
> layout are awaiting application rollout. Documentation publication does not
> establish availability in your Enduria deployment.

Open **Settings → Service Management → Ticket migration** to choose the task you
need. The workspace brings migration tools together while keeping source evidence,
operational imports and current ticket work separate. Each tool checks its own
current prerequisites; the overview does not confirm a migration or handover.

## Choose the right task

### Prepare a source transfer

- [Migration sources](./ticket-migration-sources): register an explicit source and
  account identity, then retain the declaration for your normalised manual export.
- [Migration evidence](./ticket-migration-evidence): retain and verify original
  revisions, packages and files against their recorded manifest.
- [Migration plans](./ticket-migration-plans): choose current clients, people and
  tenant destinations, give each identity a disposition and obtain independent review.

### Bring across unfinished work

- [Backlog activation](./ticket-migration-activation): create selected ordinary
  tickets or incidents with reviewed plan/evidence, rehearsal, frozen final export
  and source-closure attestations.
- [Adopt imported tickets](./ticket-migration-adoption): link an explicitly compared
  successful CSV target to reviewed source evidence, without replacing current work.
- [Correct migrated tickets](./ticket-migration-corrections): review and apply
  current text, priority or category corrections against an existing source link
  and current plan/evidence.

### Review selected work and performed handover

- [Reconcile selected tickets](./ticket-migration-reconciliation): compare the
  exact selected identity set and independently review current linked ticket work.
  Outside-selection links retain their explicit exceptions. This approval does
  not perform manual handover or source shutdown.
- [Confirm performed handover](./ticket-migration-handover): retain real earlier
  rehearsal, final export, routing and actual intake evidence for independent
  confirmation. Prepare the selected baseline after all performed checks.

### Import or inspect retained work

- [Import tickets](./ticket-imports): import operational CSV rows using explicit
  source-status mappings. **Ticket import history** retains their row outcomes.
- **Ticket migration archive**: validate and reconcile historical packages separately.

Activation and adoption are different choices for a target. Adoption preserves
existing current work; activation creates a new selected target. A standalone CSV
import does not automatically register a source transfer. A historical archive
does not create operational tickets. Imported backlog keeps **no SLA clocks**.

## Access and navigation

The workspace shows only tools allowed by your current permissions and scope.
Standalone import/history follow their existing ticket or settings management
access; the archive requires settings management. Governed source transfer,
mapping, evidence, activation, adoption, correction, selected-set reconciliation and handover require current active
unbound staff with `settings.manage`, `tickets.manage`, `tickets.view.all` and
`tickets.edit.all`. Portal customers and client-bound staff cannot administer
those governed transfer tasks. Each guide states its full requirements.

1. Open **Ticket migration** and choose the appropriate task card.
2. Complete that tool's explicit prerequisites and inspect its preview or retained
   comparison before writing or deciding.
3. Use **Ticket migration** at the top of a tool to return to the overview, or
   expand **Choose another migration task** to navigate directly.
4. Use **Search settings** to find a specific authorised tool by name. Saved
   links and existing tool URLs continue to open their original screens.

## Review a retained proposal

Opening a retained activation, adoption, correction, selected-set comparison or handover shows its review task with
new-proposal tools collapsed. Inspecting an existing proposal on the same screen
also brings its review task into focus.

1. Inspect the actual current payload or before/after comparison, destinations,
   source evidence, current readers and any blockers.
2. Enter the visible **Review action reason** and use the available independent
   decision or execution control. Opening a review never grants decision authority.
3. Expand **Propose a new activation**, **Propose a new adoption** or **Propose a
   new correction**, **Prepare a selected-set comparison** or **Prepare performed
   handover evidence**, only when preparing another proposal. Collapsing this section
   keeps your draft and command state on the current screen.

The original preview, independent review and execution rules still apply. An
activation/adoption approval is separate from execution; correction approval
applies the safe-field change immediately. Follow the specific guide for the
operation you are reviewing.

## Recover and continue safely

If a result is unconfirmed, keep the original command UUID and use that tool's
lookup or exact retry with the original account. Expanding or collapsing proposal
tools does not release the pause on new writes. Do not navigate away with an
unrecorded UUID or create a replacement command to guess the outcome.

Changed current work or source evidence requires fresh review. Retained reports
remain available in the same tool. Routing, new intake, independent handover,
source-system shutdown and application rollout remain separate operator activities.
