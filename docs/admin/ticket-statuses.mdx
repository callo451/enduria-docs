# Configure ticket statuses

Choose the names your team uses for service work and give each ticket type a valid starting status.

> **Awaiting rollout.** The default-status and transition validation described here is awaiting application rollout. Confirm availability with your Enduria administrator before relying on it.

## Before you start

You need **Manage settings** (`settings.manage`) to change ticket statuses or priorities. Staff also need access to the ticket and permission to edit it to change its status. Reopening a final ticket requires `tickets.reopen` in addition to that access.

Status names belong to your organisation. A status's **Category** describes its meaning; its **Final Status** switch determines whether it is finished. Different names can share a category.

## Set the starting status

1. Open **Settings → Tickets → Statuses**.
2. Choose **Add Status**, or edit the status you want to use.
3. Enter its **Name** and set **Category** to **Open**.
4. Turn **Active** and **Default** on. Leave **Final Status** off.
5. Choose **Create Status** for a new status, or **Save Changes** for an existing one.
6. Create a ticket to check the result.

Each ticket type needs exactly one active, applicable default. The standard creation form adds statuses for all five work-item types. Where your configuration restricts a status to particular types, check each affected type separately.

Ordinary work starts at the configured default. Approval-required requests enter their configured pending-approval status, and governed changes use their RFC policy's starting status. Those flows still require a valid default configuration; choosing a default never grants approval.

If creation reports a settings problem, correct the configuration and try again. Creating a ticket does not initialise missing statuses automatically.

For approval-required requests, also keep exactly one active, applicable status with **Category → Pending Approval**. Leave **Default** and **Final Status** off for that status. Create or edit it in the same Statuses tab. The **Approved** and **Rejected** categories are available there too; these categories are reserved for approval actions, not ordinary status edits.

## Rename a status or priority

> **Awaiting rollout.** Unique names and coordinated status and priority renaming are awaiting application rollout.

Rename an existing entry when its meaning stays the same and your team needs a different label. Status names must be unique within your organisation's status list, and priority names within its priority list. Letter casing does not distinguish names: for example, `Waiting` and `waiting` conflict. Inactive entries still reserve their names.

1. Open **Settings → Tickets → Statuses** or **Priorities**.
2. Select the pencil icon beside the entry you want to rename.
3. Change **Name** in **Edit Status** or **Edit Priority**.
4. For a status rename, leave **Category**, **Final Status**, **Pauses SLA** and **Active** unchanged. Change those settings in a separate save.
5. Choose **Save Changes**.
6. Check an existing ticket that used the entry. It should now display the new name.

A successful rename updates matching tickets together with the configuration. A status rename also carries the current RFC policy's lifecycle labels. Existing reviews retain their approved rules and evidence and continue to use the renamed status.

The rename is retained for audit. Renaming a label does not complete or reopen a ticket, replace its completion timestamps, or restart its SLA clock. Earlier ticket history and frozen selections keep the names recorded at the time.

Former status and priority names remain reserved for the same entry. You can rename that entry back to a former name, but cannot give the name to a different entry in the same list. To retire a status or priority, turn **Active** off and save; retain the entry so earlier evidence remains meaningful. Before retiring a default or automatic-action destination, configure its replacement.

## Status change rules

The ordinary ticket workspace currently offers a fixed list of status choices. It displays a custom starting status, but other custom names may not be selectable there yet. The creation preview also shows the fixed vocabulary. A listed name is not proof that it is configured: an unavailable choice is refused and leaves the ticket unchanged.

Status changes require an active status applicable to the ticket type. Ordinary edits permit movement between configured statuses subject to these rules:

- Leaving a final status requires your current `tickets.reopen` permission.
- Pending approval, approved and rejected categories are controlled by approval actions.
- A request awaiting approval cannot progress through an ordinary status edit. Cancellation remains available where permitted.
- RFC-governed changes retain their review, scheduling and implementation requirements.

Selecting the current status again does not record another status-change event. Status names alone do not grant approval or bypass a review.

## Configure destinations for automatic actions

> **Awaiting rollout.** Consistent validation across alternate creation and status-change paths, and protected completion timestamps, are awaiting application rollout.

Email intake, proactive incident alerts and the legacy ticket creation path require the same valid starting status as staff creation. Approval decisions use the applicable **Approved** or **Rejected** category. Software provisioning completion requires a final **Closed** category, and requester cancellation uses **Cancelled**. Finishing a linked appointment requires a final **Resolved** category; it cannot complete a change request. AI suggestions that wait for a reply use **On Hold**.

Keep exactly one active, applicable destination in each category needed by these actions. A missing or ambiguous destination is not chosen automatically. Correct it under **Settings → Tickets → Statuses**, then retry the refused action. A completed appointment can remain complete while its linked ticket remains unresolved; check both records.

The first entry into a final **Resolved** status records the ticket's resolution time. The first entry into another final category records its closure time. These timestamps are protected from manual replacement and remain when a ticket reopens. They describe the first recorded completion, not the latest completion cycle; SLA results use the retained lifecycle history. Existing missing historical times are not filled with an estimated date.

## Import historical tickets

Map each imported status to an active status configured for that ticket type. An old platform name is not accepted merely because it was once a default. Historical imports can use configured final statuses; the starting-status rule for new live tickets does not prevent importing completed history.

Historical imports can preserve the source resolution and closure timestamps. If the source has no timestamp, it remains unknown; the import time is not substituted. Subsequent status changes follow the same protected timestamp rules as other tickets.

## Resolve common problems

| Message or symptom | What to check |
| --- | --- |
| Creation asks for a valid default | Exactly one applicable active default must have category Open and Final Status off. |
| A name is already in use | Choose a distinct name. Check inactive entries too; changing letter casing alone does not make a name distinct. |
| A former status or priority name is unavailable | Edit the original entry to reuse its former name, or choose a different name for the new entry. |
| A status rename asks for a separate edit | Save the name change separately from changes to category, finality, SLA pausing, activity or applicability. |
| An upgrade reports duplicate configuration names | Ask your operator to review the reported status and priority conflicts, including inactive entries, and resolve them before retrying. The upgrade does not choose or rename entries automatically. |
| A selected status is unavailable | Check whether it is inactive, restricted to another ticket type, or duplicated with different letter casing. |
| A custom status is missing from the workspace picker | The ordinary workspace still offers its fixed list. Adding the status in Settings does not currently add it to that picker. |
| Reopening is refused | Ask an administrator to check your current role and `tickets.reopen` permission. |
| An approval status is refused | Use the work item's approval action. A status edit cannot record an approval decision. |
| An import row rejects its status | Correct the mapping to your organisation's configured vocabulary and retry the failed row. |
