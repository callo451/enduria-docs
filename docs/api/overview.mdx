# API overview

Enduria exposes a versioned REST API under `/api/v1`. Use it to work with tickets, comments, assets, clients, users, projects, project tasks, knowledge, time entries, reports, reference data, polling, and webhooks.

Every request is scoped to the organisation that owns the API key. A caller cannot select a different tenant with a request parameter.

The public API is separate from Enduria's staff interface, customer portal, monitoring-agent, scheduler, and provider callback routes. Those surfaces use different authentication schemes and are not interchangeable with `/api/v1`.

## Start integrating

1. Ask an administrator to create a dedicated API key with the required [scopes](./scopes).
2. Store the key in a secret manager; it begins with `en_live_`.
3. Complete the [quickstart](./quickstart).
4. Download the live [OpenAPI document](./reference) from your deployment.
5. Test against non-production data before enabling writes.

```bash
curl --request GET \
  --url "https://your-enduria.example/api/v1/tickets?limit=25" \
  --header "Authorization: Bearer $ENDURIA_API_KEY"
```

The API contract is generated by the application, so the document served by your deployment is authoritative for its installed version.

## Design principles

- **Tenant-safe:** organisation scope comes exclusively from the stored API key.
- **Configurable:** ticket and project vocabulary comes from tenant settings, not universal constants.
- **Retry-safe:** writes support idempotency keys and responses include request identifiers.
- **Extensible:** resource responses may gain fields, and JSON metadata varies by tenant and resource type.
- **Discoverable:** OpenAPI 3.0.3 and Swagger 2.0 documents are generated from the same contracts used by route handlers.

## Base URL

Join your deployment origin with `/api/v1`:

```text
https://your-enduria.example/api/v1
```

All requests should use HTTPS. Examples in this documentation use `$ENDURIA_URL` for the deployment origin and `$ENDURIA_API_KEY` for the key.
