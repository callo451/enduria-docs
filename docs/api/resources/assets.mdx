# Assets

Use `/api/v1/assets` to maintain your organisation's active asset register. Use `assets:read` for reads, `assets:write` for creation and updates, and `assets:delete` for archiving. The API key determines the organisation; a `clientId` filter does not change that boundary.

Consult your deployment's [OpenAPI reference](../reference) for the complete operations, request fields and response schemas. The workflows below explain how to use that contract without confusing register changes with physical disposal or reviewed restoration.

## Find active records

List assets with `GET /api/v1/assets`. Filter by `status`, `category`, `assignedTo`, `clientId` or `search`; the legacy `type` filter refers to category. Use the recorded category value when filtering. Category filters are exact matches, unlike the configured name/code/ID validation used on writes.

Pages default to 20 records and support 1–100 records. List and individual-record reads exclude archived assets. A record that disappears from the active register may have been archived rather than erased.

## Create a record using your configured vocabulary

Provide a name and an active configured category name, code or ID. A new asset is in the **In use** state, so `status` must be an active status of that state from [`GET /statuses?type=asset`](./configured-vocabulary#statuses); omit it to use the state's default. When you update an asset, `status` must belong to its current state; a status of another state is refused with `400`. States and the rules above require a future application release.

For example, replace the category and lifecycle placeholders before submitting:

```json
{
  "name": "Reception laptop",
  "category": "YOUR_CONFIGURED_CATEGORY",
  "status": "YOUR_IN_USE_STATUS_KEY",
  "manufacturer": "Example Manufacturer",
  "model": "ExampleBook 14",
  "serialNumber": "SERIAL-EXAMPLE",
  "specifications": {"memoryGb": 16, "encrypted": true}
}
```

Omit `assetTag` to generate one using the organisation's configured format. If supplied, `assignedTo` must identify a user in the same organisation, and `clientId` must identify one of its clients. Dates use ISO timestamps, such as `2026-10-04T00:00:00Z`.

The public API accepts the field names in its schema. Staff-interface aliases such as `categoryId`, `locationId` and `assignedUserId` are not interchangeable public API fields.

## Update or clear fields

Use `PATCH /api/v1/assets/{id}` with only the fields you intend to change. Omitted fields keep their current values. Send `null` to clear purchase or warranty dates, purchase cost, assignee, location or notes:

```json
{
  "assignedTo": null,
  "warrantyExpiry": null,
  "notes": "Assignee cleared after reviewing the register entry."
}
```

Do not send `null` for every optional field: check which fields are nullable in the live schema. `clientId` is accepted on creation but is not writable through this PATCH contract. There is no writable `type` or `department` field.

`purchaseCost` is a numeric value. The current public write schemas do not accept `purchaseCurrency`, even though an asset response may contain a recorded currency. Do not infer a currency from the API key's organisation or treat an amount with unknown currency as a converted value. Use the staff asset interface when the recorded currency needs editing.

Changing `assignedTo` is recorded in the asset's [custody history](../../product/asset-custody) with the API as its source (awaiting rollout). With that release, the user must be active and compatible with the asset's client, otherwise the request returns `400`. A customer contact must belong to the asset's own client. A new assignee also queues the `asset.assigned` webhook, which is emitted for assignments from every source, not only the API. Sending `null` clears the assignee and records the asset as unassigned. If your organisation asks for [asset acceptance](../../product/asset-acceptance) for the asset's category, a new assignee is asked to accept it and `asset.acceptance_requested` is queued; the assignment itself still takes effect immediately.

An assignment or lifecycle field update does not record recipient acceptance, verified sanitisation or disposal approval. Connector-managed devices may also receive later provider updates, so confirm which fields your connector owns before making manual changes.

## Archive an asset

`DELETE /api/v1/assets/{id}` archives the record. It retains the asset and its evidence, revokes active agent credentials and stops commands that have not yet been dispatched. Already dispatched commands may still execute.

The success data contains both `deleted: true`, retained for compatibility, and `archived: true`. **Do not interpret `deleted` as permanent erasure.** Repeating DELETE for an existing archived record succeeds without repeating the archive effect. Subsequent normal GET or PATCH requests for that record return not found, and it is absent from the active list.

Archiving does not establish physical disposal, erase a device, return inventory or release custody. See [Asset lifecycle](../../product/asset-lifecycle) for the staff archive, disposal and restoration journeys, and [Asset approvals](../../product/asset-approvals) for review settings and responsibilities. Those staff governance workflows are separate from the public API; an API key does not expose their internal routes or approve a restoration.
