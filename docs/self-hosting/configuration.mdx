# Configuration

Keep deployment configuration outside the container image and source repository. Use your platform's secret manager for credentials and encryption material.

## Configuration checklist

- Set the canonical public application URL used by authentication callbacks.
- Configure a production PostgreSQL database with durable storage.
- Set a strong `CRON_SECRET`; an unset production secret denies scheduled requests.
- Configure email delivery and inbound processing if those features are enabled.
- Choose the [file storage](./file-storage.mdx) backend and set `ENDURIA_EDITION`. The application refuses to start if storage cannot serve that edition.
- Select and configure an AI provider only if AI features are enabled.
- Set provider credentials for each external integration independently.
- Restrict any internal service secret to trusted service-to-service callers.

Restart the affected service after changing environment values. Validate `/api/health`, sign-in, and one representative background job after material configuration changes.

Refer to the release's example environment file and deployment configuration for the complete variable list; supported variables can change between releases.

## Enable MCP service connections

> **Availability:** Scoped service keys are awaiting application rollout. Existing dedicated ticket keys keep their original access.

1. Set `MCP_ENABLED=true` for the application service.
2. Set `MCP_PUBLIC_URL` to its public root address, for example `https://support.example.com/`. Do not include `/api/mcp`, credentials, a query or a fragment.
3. Use HTTPS and configure the reverse proxy to preserve the public Host header. HTTP is accepted only for loopback testing.
4. Restart the application service and verify normal sign-in and `/api/health`.
5. Ask an authorised administrator to publish service access and create a key through [Agent access](../admin/agent-access.mdx). Organisation API access must remain enabled.

The administrator copies the complete MCP address from that screen. Clients authenticate each request with a Bearer key. JSON Streamable HTTP is supported; GET event streams and delegated OAuth sign-in are not available in this increment. Allowed reads and preparation of reviewed ticket changes do not require Enduria to call an AI model provider. A signed-in staff reviewer approves changes in Enduria; the Bearer key cannot make that decision.

## Run built-in ticket triage

> **Availability:** The durable ticket-triage workflow is awaiting application rollout.

Apply the release's committed database migrations, configure an AI provider and keep the bundled scheduler running with the same `CRON_SECRET` as the application. The scheduler's manifest includes `/api/cron/agent-triage` every minute. Existing self-hosted Workflow SDK configuration also applies; retain its durable PostgreSQL world across restarts.

An authorised administrator enables classification and publishes one [built-in ticket-triage workflow](../admin/agent-access.mdx#set-up-built-in-ticket-triage). MCP configuration and a service key are not required for this workflow. Verify it with one new in-scope ticket: queued work should advance to a suggestion or a recorded unavailable, stale, failed or expired state. Check scheduler and application health when pending work does not advance.

The workflow retains creation intents and provider-attempt claims. Recovery does not resend an uncertain model attempt. Disable its published access to stop pending work, then inspect retained outcomes; do not delete claims or run historical tickets through it to force a retry. Disabling classification is an additional stop control.
