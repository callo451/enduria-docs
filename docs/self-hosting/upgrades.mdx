# Upgrades

Plan application and schema upgrades together. Enduria commits SQL migrations as the supported database upgrade path.

## Upgrade procedure

1. Read the release notes and identify configuration or compatibility changes.
2. Arrange a maintenance window and stop the application instances and scheduler. Back up the database, user-managed file storage and protected recovery configuration together; follow the [backup and isolation procedure](./backups.mdx).
3. Confirm the backup can be restored and record the currently deployed version.
4. Pull or build the intended release image.
5. Run the one-shot migration service successfully.
6. Start the application and scheduler services.
7. Check `/api/health`, authentication, a tenant-scoped read, and scheduled processing.
8. Monitor logs and key workflows before declaring the upgrade complete.

If an upgrade fails after a migration, keep the application and scheduler stopped and use the release-specific recovery guidance. Preserve the failed command's result and inspect migration completion before retrying the guarded command. Do not assume that deploying an older image against a newer schema is safe. A rollback may require restoring the pre-upgrade database backup into an isolated target and reconciling later external activity before restarting workers.

## Migration history checks

> **Awaiting rollout.** The migration history verification described below is awaiting application rollout. Confirm that your release includes it before relying on these checks.

Use the one-shot migration service for Docker Compose installations, or **`npm run db:migrate`** for a source installation. The supported command checks that previously applied migrations match the release before applying pending changes, and verifies completion afterward. A recognised migration ordering correction is handled automatically; you do not need to replay earlier migrations.

If the command reports that stored migration history does not match the release, stop the upgrade and keep the error message. Confirm that you are using the intended release and its unchanged migration files. Preserve your database backup and contact support or your deployment maintainer for release-specific recovery guidance. Do not delete migration history, edit previously applied migrations, or manually mark migrations as applied to bypass the refusal.

Start the application only after the migration service succeeds. A migration failure may require correcting the deployment files or restoring the pre-upgrade backup; changing the application image alone does not undo database changes.

## Ticket reporting verification and recovery

> **Awaiting rollout.** Ticket reporting input verification and the recovery functions below are awaiting application rollout. Confirm that the deployed release includes them before using these steps.

The upgrade prepares ticket reporting inputs from current operational tickets and their existing recorded facts. Ticket reports verify those inputs before using them. The first report after an application restart can take longer while verification runs. An unavailable report must not be interpreted as zero work or a zero-percent outcome.

This procedure requires an authorised database operator and access to the intended deployment's PostgreSQL database. SaaS administrators should contact their deployment provider. Keep a current backup and arrange a maintenance window: repair temporarily makes ticket and fact writers wait while it verifies a consistent source.

1. Confirm the intended release and a successful migration run. If the upgrade or restore failed, resolve that failure first.
2. In a database session for that deployment, replace `ORG_UUID` below with the intended organisation's UUID. The first query must return the organisation you intend to inspect:

   ```sql
   SELECT id, name FROM organizations WHERE id = 'ORG_UUID'::uuid;
   SELECT verify_ticket_metric_sources('ORG_UUID'::uuid);
   ```

3. If verification returns `false`, repair the derived reporting inputs and verify again:

   ```sql
   SELECT rebuild_ticket_metric_sources('ORG_UUID'::uuid);
   SELECT verify_ticket_metric_sources('ORG_UUID'::uuid);
   ```

   The repair returns a changed-row count, which can be zero when inputs already agree. Require verification to return `true`. An error or missing result is not a successful check.
4. Restart the application instances after a restored database or a repair, then sign in and retry a representative tenant-scoped ticket report with the intended period and filters.
5. If reporting remains unavailable, preserve the error and deployment logs and seek release-specific recovery assistance. Keep the released database protections enabled. Do not edit migration receipts, disable constraints or alter original ticket history to bypass refusal.

This repair copies existing operational records and facts. Missing history stays unknown; it does not reconstruct transitions or policy decisions, create SLA clocks for imported backlog, materialise archive-only records or change source-system routing.
